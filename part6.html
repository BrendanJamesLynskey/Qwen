01

The three models, and which one you want

The Qwen3-Coder line comprises three open checkpoints, all Apache 2.0, all instruct-only — none of them generate <think> blocks. That last point surprises people: the strongest open coding model in the family does not reason out loud, because its post-training put the deliberation into the tool loop rather than into a monologue.

ModelTotal / activeContextBF16 weightsRealistic deployment
Qwen3-Coder-480B-A35B-Instruct480B / 35B256K → 1M~960GB8×H200 at FP8, or multi-node BF16. A serious cluster.
Qwen3-Coder-30B-A3B-Instruct “Flash”30B / 3B256K~60GB1×80GB BF16, or a 24GB card at 4-bit. The one most people run.
Qwen3-Coder-Next80B / 3B256K~160GB2×80GB. Feb 2026 — flagship quality at Flash-class compute. See slide 09.

Choose 30B-A3B if…

You want a self-hosted coding assistant on hardware you already own, or an inline completion backend where latency dominates. 3B active means genuinely fast decode; quality is good rather than frontier.

Choose 480B-A35B if…

You are running an autonomous agent on real repositories and correctness per attempt matters more than cost per token. This is the checkpoint that posts the headline SWE-bench numbers.

Choose Coder-Next if…

You want the 480B's agentic quality without the 480B's bill. Same or better SWE-bench at a fifth of the memory and a tenth of the active compute. In 2026 this is the default recommendation.

Tokenizer warning

Qwen3-Coder introduced new special tokens and reassigned token IDs relative to Qwen3. You must use the tokenizer shipped with the checkpoint and transformers ≥ 4.51.0; older versions raise a KeyError, and — worse — a stale cached tokenizer can silently mis-encode tool-call delimiters, producing calls that never dispatch.

02

Architecture of the 480B-A35B

Structurally this is a Qwen3 MoE, scaled up and re-proportioned: fewer, larger experts than the general Qwen3 (160 rather than 128, with 8 active), a much deeper stack, and a native context four times longer.

Note the data mixture: 7.5 trillion tokens at roughly 70% code. Qwen2.5-Coder was used to clean and rewrite noisy source data before training — the same generation-over-generation data flywheel described in Part 05, applied to the coding corpus.

03

How it was trained — 20,000 environments in parallel

The pre-training is unremarkable in kind, if large in degree. The post-training is where Qwen3-Coder separates itself from every previous coding model, and it has two distinct reinforcement-learning phases.

Why episode-level reward changes behaviour

Rewarding individual steps teaches a model to look like a competent engineer. Rewarding only the final outcome teaches it to be one — including the unglamorous parts: re-reading a file it already read, backing out a change that made things worse, and noticing that the test failure is in a different module than the one it edited. That is why Qwen3-Coder recovers from errors in ways Qwen2.5-Coder simply could not.

04

Benchmarks, and the harness caveat

Qwen3-Coder-480B-A35B-Instruct reached 69.6% on SWE-bench Verified at release — state of the art among open models without test-time scaling, and comparable to Claude Sonnet 4 at the time. It set records among open models across a dozen benchmarks covering agentic coding, agentic browser use and agentic tool use.

Read SWE-bench numbers with care

SWE-bench Verified is an agent benchmark, not a model benchmark. The same weights score differently under different scaffolds: Qwen3-Coder-Next is reported at 70.6 with SWE-Agent, 71.1 with mini-SWE-Agent, 71.3 with OpenHands and 74.2 under its best harness. Turn limits matter too — the 480B's 69.6 was measured with up to 500 interaction rounds. When comparing models, insist on the harness and the turn budget, or you are comparing scaffolds.

05

Abilities — what it can actually do

Agentic software engineering

The headline capability. Given an issue and a repository, it explores, plans, edits across multiple files, runs builds and tests, reads failures and iterates. Sustains hundreds of turns without losing the thread — the single biggest jump over Qwen2.5-Coder.

Repository-scale comprehension

256K native context holds a mid-sized codebase outright. With YaRN to 1M you can put a large monorepo subtree, its tests and its docs in one prompt — though see the cost caveat on the next slide before you do.

Tool use and function calling

A dedicated XML-flavoured tool-call format with its own parser in vLLM and SGLang. Trained for parallel calls, for recovery when a call errors, and — importantly — for not calling tools it does not need.

Browser and computer use

The agentic RL generalised beyond code. The 480B set open-model records on agentic browser-use benchmarks, making it viable as the reasoning core of a web-automation agent, not only a coding one.

358 programming languages

Nearly four times Qwen2.5-Coder's 92. Coverage of long-tail languages — Verilog, Terraform, COBOL, R, Elixir — is meaningfully better, though quality still tracks corpus volume, so mainstream languages remain far stronger.

Fill-in-the-middle

Inherited from the Qwen2.5-Coder line and still present, so the same weights can back both an agent and an inline-completion endpoint. In practice you would use the 30B-A3B for completion — the 480B's latency makes no sense there.

Drop-in client compatibility

The line ships with Qwen Code, a terminal agent adapted from Gemini CLI with a rewritten parser and tool layer. But the models also work behind Claude Code and Cline via an OpenAI-compatible endpoint — whether that is your own vLLM server or Alibaba's DashScope API. For most teams, pointing an existing agent client at a self-hosted Qwen3-Coder is the fastest path to evaluating it honestly on their own repositories.

07

Pros and cons, honestly

Strengths

  • Genuine multi-turn agency. It recovers from its own mistakes. This is qualitatively different from every open coding model before it, and it is the reason it works in real agent harnesses.
  • Frontier-adjacent at Apache 2.0. Comparable to a leading closed model of its era with no licence terms to negotiate and no data leaving your network.
  • Real long context. 256K native, trained rather than extrapolated — a repository actually fits.
  • Cheap decode for its size. 35B active out of 480B; the 30B-A3B and Coder-Next take that further.
  • Ecosystem fit. Works behind Qwen Code, Claude Code and Cline; day-one vLLM and SGLang support with a dedicated tool parser.
  • No thinking tax. Instruct-only means no invisible reasoning tokens inflating the bill on every turn.

Weaknesses

  • The 480B is genuinely expensive to host. ~960GB BF16, ~480GB FP8. Below a multi-GPU H200-class node it is not a self-hosting option, and it competes on cost with simply buying API tokens.
  • KV cache dominates at long context. ~33 GiB per sequence at 256K means concurrency collapses precisely when you use the feature you bought it for.
  • No reasoning mode. For algorithmic puzzles or deep debugging that benefits from deliberation, a Thinking-2507 or Qwen3.6 model is stronger.
  • 1M context is extrapolated, not native. YaRN degrades short-context quality when applied statically, and quality at the far end of a million tokens is not the same as at 256K.
  • Long-tail language quality is uneven. 358 languages is a coverage claim, not a quality claim.
  • Superseded on efficiency. Since February 2026, Coder-Next matches it at a fraction of the cost. The 480B is now mainly of interest for reproducibility and comparison.
The honest 2026 recommendation

If you are starting today: run Qwen3-Coder-Next if you want a dedicated coding agent, or Qwen3.6-27B if you want one model that codes well and reasons. Deploy the 480B only if you have the hardware idle and need the specific checkpoint. Deploy the 30B-A3B if your constraint is a single consumer GPU.

vLLM support, capability by capability

Qwen3-Coder is exceptionally well served by vLLM — the tool parser was contributed alongside the model release. Not every capability is equally mature, so here is the honest per-feature assessment.

The one bug class to know about

There is a known failure mode across Qwen tool-calling deployments where XML tool-call markup emitted inside a reasoning region is not extracted — the response arrives with populated reasoning_content and an empty tool_calls array. It does not affect Coder models, which have no reasoning region, but it does affect thinking-capable Qwens with XML-style parsers. If you see silently dropped tool calls, check that pairing first.

Why this matters more than the score

Between July 2025 and February 2026 the Qwen coding line got slightly better on benchmarks and roughly twelve times cheaper to run per token, with a six-fold smaller memory footprint. That is the whole thesis of the 2026 generation, and it comes entirely from the hybrid-attention MoE architecture — which is what Part 07 is about.
