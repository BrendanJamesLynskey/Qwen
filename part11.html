01

Why vLLM, and the first check to run

vLLM and SGLang are Qwen's two first-party production targets. Both get official recipes per model; both usually land support on or near release day. This deck focuses on vLLM, but the concepts and most flags map directly onto SGLang.

What vLLM gives you for Qwen specifically

  • PagedAttention — KV cache in fixed blocks, so no per-sequence over-allocation. The reason 262K contexts are servable at all.
  • Continuous batching — requests join and leave the batch per step rather than per request.
  • Automatic prefix caching — shared prompt prefixes computed once. Enormous for agents, which re-send system prompts and tool schemas every turn.
  • Chunked prefill — a 200K-token prompt is split so it cannot block every other request in the queue.
  • Qwen-specific parsers and kernels, contributed alongside the model releases.

The version question, first

Qwen ships new architectures frequently, and each needs code in vLLM. Before anything else, check the model card's stated minimum version — and pin it.

# indicative minimums from model cards
Qwen3          → any recent vLLM
Qwen3-VL       → ≥ 0.11.0
Qwen3-Next     → nightly at launch, now stable
Qwen3-Coder-Next → ≥ 0.15.0
Qwen3.5 / 3.6  → ≥ 0.17.0

If vllm serve fails with “Model architectures [...] are not supported”, that is a version problem, not a configuration problem. Upgrade — and be aware new architectures sometimes land in nightly weeks before stable.

Operational advice

Pin your vLLM version and test upgrades deliberately. Hybrid-attention models, MoE kernels and tool parsers are all comparatively young code. Tracking latest gets you new capability and new regressions in the same commit; the Qwen recipes exist precisely because the version matters.

Parsers — the most error-prone thing in the stack

Two independent parsers sit between the model's raw token stream and your API response. Choosing them wrongly produces failures that look like model failures, and they are the single most common Qwen deployment mistake.

A real bug worth knowing

There is a reported failure where a model emits XML tool-call markup inside its <think> region: the reasoning parser claims the whole region, the tool parser never sees the markup, and you get populated reasoning_content with an empty tool_calls array — no error anywhere. If tool calls vanish intermittently on a thinking model, this is the first thing to check, and the fix is usually a version pin or a parser swap.

04

Parallelism: TP, PP, EP and DP

Four independent axes, each solving a different problem. Choosing the wrong one for a 512-expert model can cost you most of the performance you paid for.

Tensor parallel — --tensor-parallel-size

Split every weight matrix across GPUs; every GPU participates in every layer. All-reduce at each layer, so it wants fast interconnect (NVLink). The default choice for dense models too large for one card. Latency improves; communication cost grows with the degree.

Pipeline parallel — --pipeline-parallel-size

Split by layer: GPU 0 holds layers 1–20, GPU 1 holds 21–40. Communication is a single activation hand-off per boundary, so it tolerates slow interconnect — the right axis across nodes. Costs pipeline bubbles unless the batch is large.

Expert parallel — --enable-expert-parallel

Split by expert: each GPU owns a subset of the experts, and tokens are routed to the GPU that holds theirs. The right topology for high-sparsity MoE — a 512-expert model split by tensor parallelism has every GPU holding a sliver of every expert, which is all communication and no locality. Composes with TP.

Data parallel — --data-parallel-size

Replicate the model and split the requests. Pure throughput scaling with no communication, when the model fits on one device. For small Qwens this beats tensor parallelism outright: four independent 9B replicas serve far more traffic than one 9B sharded four ways.

The decision, as a rule
# Fits on one GPU?                    → replicate, don't shard
vllm serve Qwen/Qwen3.5-9B --data-parallel-size 4

# Dense, too big for one GPU, one node → tensor parallel
vllm serve Qwen/Qwen3.6-27B --tensor-parallel-size 2

# Sparse MoE, one node                → tensor parallel + expert parallel
vllm serve Qwen/Qwen3.5-397B-A17B --tensor-parallel-size 8 --enable-expert-parallel

# Too big for one node                → pipeline across nodes, tensor within
vllm serve Qwen/Qwen3-Coder-480B-A35B-Instruct \
  --tensor-parallel-size 8 --pipeline-parallel-size 2 --enable-expert-parallel
The most common mistake

Reaching for tensor parallelism on a model that already fits. Sharding a 9B across four GPUs makes each token slightly faster and your aggregate throughput much worse, because you have added an all-reduce to every layer for no memory benefit. Shard only when you must.

05

Where the memory goes

Almost every vLLM problem is a memory problem, and almost every memory problem is the KV cache. Being able to compute it in your head is the most useful skill in this deck.

Why hybrid attention changes your capacity planning

Compare the first two boxes. The same nominal 262K context costs roughly four times less KV cache on a hybrid model, because three quarters of the layers hold a constant-size recurrent state instead. Concurrency scales with that saving. If you sized a cluster using a Qwen2.5-era spreadsheet, a 2026 model will comfortably beat your estimate — verify before you buy hardware.

The MoE caveat

Quantising a mixture-of-experts is not the same as quantising a dense model. The router is a small matrix whose outputs determine which experts fire — a quantisation error there does not perturb an activation slightly, it selects a different expert. Good MoE quantisation keeps the router and the shared expert at higher precision. Prefer official or well-tested community checkpoints over rolling your own for MoE.

What quantisation does not fix

It shrinks weights, not the KV cache. If you are OOM at 262K context on a model whose weights already fit, 4-bit will not help — you need a shorter --max-model-len, fewer concurrent sequences, or KV-cache quantisation, which is a separate feature with its own quality trade-off.

A structural advantage in the 2026 models

Qwen3-Next onwards use zero-centred RMSNorm with weight decay and gated attention outputs specifically to suppress activation outliers (Part 07, slide 05). Outliers are the main thing that makes post-training quantisation lossy — so these models quantise better than their predecessors almost as a side effect of being trainable at all.

08

Speculative decoding and MTP

Decoding is memory-bandwidth bound: each step reads the entire active parameter set to produce one token. Speculation amortises that read across several tokens.

MTP — the model drafts for itself

Qwen3-Next, Qwen3.5 and Qwen3.6 are trained with multi-token-prediction heads, so no separate draft model is needed. Acceptance rates are high because the drafter is the model.

# Qwen3.5 / 3.6
--speculative-config '{"method":"mtp",
   "num_speculative_tokens":1}'

# Qwen3-Next
--speculative-config '{"method":"qwen3_next_mtp",
   "num_speculative_tokens":2}'

Draft-model speculation — for models without MTP

Pair a large model with a small one from the same family and tokenizer: a Qwen3-0.6B drafting for a Qwen3-32B. Works, but acceptance is lower than MTP and you must match tokenizers exactly — which rules out mixing a Qwen3-Coder (retokenised) with a Qwen3, or a Qwen3 with a Qwen3.5 (250K vocabulary).

When to enable it, and when not

Enable for low-concurrency, latency-sensitive endpoints — an interactive coding agent, a voice front-end, anything a human is waiting on. It reduces time-per-output-token with a high acceptance rate. Disable for high-throughput batch workloads: verification work competes with real work, and aggregate tokens per second falls. The vLLM recipes also suggest turning prefix caching off alongside MTP when chasing minimum latency — measure both ways on your own traffic.

Correctness

Speculative decoding is distributionally exact. Rejected drafts are discarded and resampled by a scheme that preserves the target model's output distribution — so this is a pure latency optimisation, not a quality trade. If output changes when you enable it, that is a bug, not a design property.

Multimodal, embedding and scoring

Three different runners, three different endpoints
# 1. Generative multimodal — /v1/chat/completions with image_url content parts
vllm serve Qwen/Qwen3-VL-8B-Instruct \
  --limit-mm-per-prompt '{"image": 4, "video": 1}' \
  --max-model-len 65536

# 1b. A natively multimodal Qwen3.5/3.6 used for text only — skip the vision tower
vllm serve Qwen/Qwen3.6-27B --language-model-only

# 2. Embeddings — a pooling model on /v1/embeddings
vllm serve Qwen/Qwen3-Embedding-0.6B --task embed

# 3. Reranking — a scoring model on /v1/score
vllm serve Qwen/Qwen3-Reranker-4B --task score
