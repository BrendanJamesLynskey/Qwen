Sizing the hardware

Weight memory is straightforward arithmetic: total parameters × bytes per parameter. Active parameters do not reduce it — every expert must be resident. Then add the KV cache, which is what usually decides the answer.

Then add the KV cache — and it is often the bigger number

From Part 11: 2 × layers × kv_heads × head_dim × bytes per token, times your context, times your concurrency. On a full-attention model at 262K context that can exceed the weights. On a hybrid-attention model only a quarter of the layers contribute, which is a large part of why the 2026 family is so much cheaper to serve at long context. Never size a deployment on weight memory alone.

A quick sanity rule

Budget roughly: weights + (bytes_per_token × max_model_len × expected_concurrent_sequences) + ~10% headroom. If that exceeds your HBM, reduce --max-model-len before you reduce precision — context is usually the cheapest thing to give up, and quantisation costs quality everywhere at once.

04

Dense or sparse — a rule that actually works

Qwen3.6 shipped both a 27B dense and a 35B-A3B sparse model in the same month, and the dense one won on coding while the sparse one wins on cost. That is not a contradiction — they optimise different things.

Choose dense when…

  • Per-token reasoning quality dominates. Every parameter computes on every token
  • Latency must be consistent. No routing variance, no all-to-all communication
  • The session is long and sequential — agentic coding, multi-turn tool use
  • Deployment must be simple. Uniform sharding, no expert parallelism, better support in edge runtimes
  • Memory is tight relative to compute — a dense 27B beats a sparse 122B you cannot fit

Choose sparse MoE when…

  • Throughput per dollar dominates. 3B of work per token at 35B of knowledge
  • Knowledge breadth matters more than depth — RAG, classification, broad-domain chat
  • You have memory to spare and want the most capability that fits in it
  • Concurrency is high. Sparsity's advantage compounds across a large batch
  • You can run expert parallelism — multi-GPU with decent interconnect
The one-line version

Total parameters buy knowledge and cost you memory. Active parameters buy reasoning and cost you time. Pick the axis your workload is actually bounded on, then pick the largest model on that axis that fits your hardware.

And measure it yourself

Both models above are Apache 2.0 and both run on the same vLLM command with one word changed. Benchmarks are harness-dependent and your workload is not SWE-bench. An afternoon comparing the two on your traffic is worth more than any table in this series.

05

Self-host or API

Self-hosting wins on

  • Sustained high volume. A GPU costs the same whether it is busy or idle, so heavy steady traffic amortises it
  • Data residency. Nothing leaves your network — often the whole reason the question is being asked
  • Latency floor. No network hop, no queue you do not control
  • Determinism and pinning. The model does not change under you on someone else's schedule
  • Fine-tuning. Your adapters, your weights, your evaluation

The API wins on

  • Spiky or low volume. Paying per token beats paying for idle H100s
  • Frontier capability. The Max tier has no open equivalent, by design
  • Time to first value. No cluster, no ops, no capacity planning
  • Very long context occasionally. 1M-token windows are expensive to provision and cheap to rent
  • Cached-input pricing. Qwen3.8-Max reads cached input at $0.25 per million against $2.00 uncached — hard to beat for repetitive agent prefixes

The break-even, done honestly

Take an 8×80GB node. Compare its fully-loaded hourly cost — rental or amortised purchase plus power, cooling and an engineer's attention — against the token throughput you can actually achieve at your context length and concurrency, priced at the API rate for a comparable model. Two things distort this calculation more than anything else:

  • Utilisation. Self-hosting only wins if the GPUs are busy. A node at 15% utilisation is far more expensive per token than any API.
  • Thinking tokens. If you run a reasoning model, most of your output tokens are invisible. Meter reasoning_content separately before you model API cost, or you will underestimate it by a large factor.
The pattern most teams land on

Self-host an open Qwen for the bulk of traffic behind an OpenAI-compatible endpoint, and route the small fraction of genuinely hard requests to the Max tier through the same interface. Because both speak the same API, that routing is a configuration decision you can change weekly — and it lets you measure exactly how many requests actually need the frontier. For most products, it is fewer than expected.

Fine-tuning — when, and with what

You want…Do thisNot this
The model to know your documentsRAG — embeddings and a rerankerFine-tuning. It teaches style far more reliably than it teaches facts
A specific output formatStructured output / guided JSON, or a few-shot promptFine-tuning for something a grammar constraint guarantees
A consistent tone or personaLoRA on a few thousand curated examplesA 4,000-token system prompt on every request
Domain vocabulary and conventionsLoRA, or continued pre-training if you have billions of tokensPrompting your way around a genuine distribution gap
A smaller model to behave like a bigger oneDistillation — generate traces from the large model, train the small oneHoping a 4B will match a 27B with better prompts
Better tool-calling on your specific toolsLoRA on real successful trajectories from your own systemFine-tuning on synthetic tool calls that do not match your schemas

Unsloth

The fastest path to a LoRA on a single GPU, with day-one support for new Qwen generations and memory optimisations that make a 27B trainable on hardware that has no business training a 27B.

LLaMA-Factory / ms-swift

Broad, configuration-driven training across SFT, DPO and friends, with strong Qwen coverage. ms-swift is Alibaba's own, so it tracks new releases closely.

TRL / Axolotl

The Hugging Face-native route. More control, more code, better when you need a custom loss or a non-standard RL setup.

Two Qwen-specific gotchas

Chat template drift. Train with the exact template the checkpoint ships and serve with the same one. A mismatch between training and serving templates is the most common cause of a fine-tune that mysteriously underperforms.

Thinking-mode data. If you fine-tune a thinking-capable model on data that contains no <think> blocks, you will quietly train the reasoning behaviour out of it. Include traces in your training data, or accept that you have made an instruct model.

Surviving a generation upgrade

Qwen ships a new generation roughly quarterly. Most upgrades are drop-in; some are not, and the naming does not reliably tell you which.

UpgradeDifficultyWhat breaks
Qwen2.5 → Qwen3moderateThinking mode is new — add a reasoning parser and decide a default mode. Tokenizer unchanged, so adapters and caches survive
Qwen3 → Qwen3 2507easyHybrid switch removed — pick the Instruct or Thinking checkpoint explicitly. Context doubles to 262K
Qwen3 → Qwen3-NextmoderateNew architecture: check the vLLM version, consider enabling MTP, re-tune memory settings
Qwen3 → Qwen3.5majorNew tokenizer (~250K vocabulary). Re-tokenise corpora, retrain adapters, re-baseline evaluations, rebuild draft models and token-ID-dependent tooling
Qwen3.5 → Qwen3.6easySame architecture family and tokenizer. Optionally adopt preserve_thinking
Qwen3-Coder → Coder-NextmoderateDifferent sampling parameters, different architecture, vLLM ≥ 0.15.0. Same tool-call parser
A migration procedure that works
  1. Build an evaluation set from your own traffic first. Two hundred real requests with graded answers beats any public benchmark for this decision.
  2. Stand the new model up beside the old one, on the same hardware profile, and shadow real traffic to it.
  3. Compare cost as well as quality. Token counts change with the tokenizer; thinking behaviour changes with the generation. A "better" model can be more expensive per resolved task.
  4. Re-tune the serving flags. Sampling parameters, parsers and memory settings are per-model, not per-family.
  5. Keep the old deployment warm until the new one has run a full traffic cycle. Rollback should be a config change.
08

The production checklist

Before you launch

  • vLLM version pinned, and the model card's minimum verified
  • --reasoning-parser set if the model thinks — and not set if it does not
  • --enable-auto-tool-choice and the correct --tool-call-parser, tested end to end with a real tool
  • Sampling parameters copied from the model card. Not temperature 0 on a thinking model
  • --limit-mm-per-prompt on every multimodal endpoint
  • --max-model-len sized against measured KV-cache use at target concurrency, not the model's maximum
  • --enable-expert-parallel on multi-GPU MoE
  • Prompts ordered stable-first so prefix caching can work

Once it is live

  • Meter reasoning_content tokens separately — usually the majority of the bill
  • Alert on prefix cache hit rate; a sudden drop means a prompt-template change
  • Alert on preemption rate; it means the KV cache is exhausted and throughput is collapsing
  • Track p50 and p99 latency — thinking models have an order-of-magnitude spread
  • Cap max_tokens per route; unbounded reasoning on a pathological prompt returns nothing at full price
  • Log the tool-call failure rate; silent parser mismatches show up here first
  • Keep an evaluation set from real traffic and re-run it on every model or version change
The five most common self-inflicted failures, in order

1. Missing or mismatched tool-call parser — tool calls silently never dispatch. 2. Temperature 0 on a thinking model — loops and repetition. 3. No multimodal cap — one user's photo takes the server down. 4. Sizing on weight memory alone — OOM the moment concurrency rises. 5. A timestamp at the top of the system prompt — a 0% prefix cache hit rate and several times the expected bill.

The one thing to take away

Everything in this series is a snapshot. The durable parts are the mechanisms: what grouped-query attention does to a KV cache, why a delta rule makes linear attention retrievable, why episode-level rewards produce agents that recover from mistakes, why total parameters cost memory and active parameters cost time, and why a mismatched parser fails silently. Model names will change quarterly. Those will not.
